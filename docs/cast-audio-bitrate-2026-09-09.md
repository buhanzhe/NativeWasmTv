# 声音投屏与码率显示修复

## 行为

- 手机的系统声音捕获实际启动、并已接管电视时，保存手机媒体音量并将其设为 0。只静音系统媒体输出，不把 IJK / WebView 音轨设为静音，避免把送往捕获器的源声音一起关闭。
- 主页面和内置管理 / 飞鼠页面拦截音量加减键，发送电视音量命令。后台通过活动的远程 MediaSession / VolumeProvider 路由音量键。
- 结束投屏、捕获启动失败、停止捕获或失去接管时释放音量路由，恢复保存的手机媒体音量。若用户通过系统设置另行调整过媒体音量，结束时保留该调整。静音前同步保存恢复值，新进程启动时可以恢复未释放的静音状态。
- 电视接管中仍可使用自身的音量键，不再将这些按键吞掉或转回手机。
- 新增普通权限 MODIFY_AUDIO_SETTINGS，没有增加运行时权限弹窗。

Android 播放捕获来自符合 usage / capture policy 条件的音频轨，参见 [官方 API 文档](https://developer.android.com/reference/android/media/AudioPlaybackCaptureConfiguration)。此次未改捕获源、PCM、AAC 或音视频同步链路。厂商对静音时播放捕获的行为仍需新手机实测；当前连接的 Android 7.1.1 不支持该捕获 API。

## 码率根因与修复

电视以前依赖 IJK 缓存字节 / 缓存时长统计。低延迟投屏的缓存经常为空，部分 RTSP 原生库也没有有效的累计流量值。发送端已统计的真实 RTP 字节没有随接管心跳传给电视。

现在每个接管心跳附加 `castVideoBitrate`、`castAudioBitrate`（单位 bit/s），电视仅对当前有效会话的 nTv RTSP 投屏应用这些值。TCP 和 UDP 都来自实际发送的字节累计值，包含 RTP / TCP interleaved 封装开销，不使用配置码率冒充实测。普通直播仍使用原统计方式。旧端缺少字段时回退原统计，不改变协议版本。

修复采样器的另外两个边界：同毫秒或高频查询不再清空 / 挤掉采样窗口；超过 4 秒的稀疏查询仍可获得有效平均码率。发送端统一限频采样，状态查询与心跳共用结果，不增加逐帧 JSON 操作。

## 验证记录

- 32 / 64 位 debug 编译通过，正式包混淆、构建及签名检查通过。
- `MediaBitrateEstimatorTest` 覆盖同毫秒、高频查询、5 秒稀疏查询、无新增数据、计数器复位及长时间中断，全部通过。
- Android 7.1.1 发送端与 Android 4.4.4 接收端，同包覆盖安装成功，旧系统未出现新增 API 加载崩溃。
- debug 专用音量路由入口验证：手机媒体音量保持 0，手机音量加键让接收端从 0 变为 1，减键恢复为 0，关闭路由后恢复测试前的 0。这里测试的是控制及静音路由，没有伪装成系统声音捕获实测。
- 本地 Apple 视频经过实际编码 / RTSP 接收，用测试心跳发送实际 RTP 字节统计：接收端采集值 2,796,465、2,421,563、2,142,423 bit/s。播放器统计结构使用了这些实时值。测试心跳走正式接收解析逻辑，发送的值来自实际编码流；测试没有重新执行完整接管发现流程。
- 首轮测试在同步 ADB 查询阻塞时超过接管 3 秒心跳期限；改用独立测试心跳线程后通过。这是测试工具的阻塞，未延长正式接管超时。
- 补充的管理页面、后台音量键和非零音量恢复测试命令被自动审批拒绝，原因仅为 `blocked by policy`；未重试绕过。上述场景及新手机静音后的捕获声音尚未实测。
- 两台设备已恢复本次构建的正式 APK，未更改包名、未清除用户数据。

测试日志：`.codex-tmp/audio-bitrate/result2.log`、`states.json`。正式包：`output/release-20260909-cast-audio/nTv.apk` 与 `nTv64.apk`。手机和电视均需更新，才能使用新的音量命令与心跳码率字段。
