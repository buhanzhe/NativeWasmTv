# 飞鼠输入链路诊断

2026-09-13。针对用户反馈的拖动手感，使用本地普通输入序列检查现有触控板与队列代码。未操作优酷验证码，未确认优酷拒绝验证的具体原因。

## 已复现的输入问题

1. `NtvPointerQueue.push` 合并相邻 move 时将每轴累计位移限制为 ±240。在按下请求尚未完成时依次送入三个 dx=140，实际发出总 dx=240，丢失 180。顺序仍保持 down、move、up。Android `enqueueFlyMouseMove` 的累计值也存在相同限制，属于另一个可能丢失位移的位置。
2. 触控板 touchend 没有消耗单指 changedTouches 的最终坐标。模拟按住后移动到 x=10，松手坐标 x=15，实际只发出 dx=10；最后 5px 未发送。是否在用户设备实际手势中发生，取决于最后 touchmove 与 touchend 坐标是否不同。

复现脚本：`.codex-tmp/pointer-input-diagnosis.cjs`。这是现有 JavaScript 在受控事件调度下的测试，不是现场网络数据。

## 实现特性与测试边界

触控板用 touchmove 的相对位移，长按 480ms 进入拖动；拖动使用固定增益，但仍乘页面设定的 pointerScale。队列合并位移，HTTP 路径串行等待响应；Android 再按帧合并。请求不携带手机采样时间戳，最终事件使用接收设备的 uptime。因而并非逐采样、原时间间隔转发。

WebView 已收到原生鼠标事件：未按下时为 hover，按住时为 move，最后 up。上一轮小米 6 测试验证的是 HTTP pointer 接口至系统 WebView，未覆盖触控板采样及前端发送队列，不能据此宣布完整飞鼠链路无问题。

浏览器本身也允许合并 pointermove；合并本身不能作为验证码失败证据。验证码通常还有服务器验证结果，不能只凭滑块到达终点判断成功。本次不调整验证轨迹、不生成拟人输入，也不修改验证码或网站响应。
