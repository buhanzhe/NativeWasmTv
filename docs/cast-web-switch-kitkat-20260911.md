# Android 7.1.1 → Android 4.4 网页切换检查

设备：MI 6（ff0316c7，7.1.1）发送，SM-G3608（8ba8ceb8，4.4.4）接收；路由器 Wi-Fi，H.264 / TCP，1280×720，25fps，3Mbps。两端覆盖安装同包名构建，通过 ADB 转发控制接口模拟选台，并读取 logcat、播放器状态和设备截图。

## 定位

初次连接曾记录“等待手机解析频道超时”。之后普通切换及快速切换未复现永久卡死/ANR，因此不能断言已经完全定位用户遇到的永久卡死。

确定的停顿路径：手机复用 WebView 和编码串流切换网页，但电视 startChannel 无条件 releasePlayer，重新创建硬件解码器及 RTSP 连接。优化前四次切换在约 2～3 秒的采样点重新 prepared。网页加载时间与串流恢复时间不同，不能混算。

## 修改

- 手机编码器每次启动生成独立 castSessionId。电视核对会话、RTSP 地址、TCP/UDP、播放器运行状态，全部相同才保留解码器。旧手机不提供标识时沿用原流程。
- 保留解码器时不更换播放生命周期 ID，使现有 EOF/error 恢复回调继续有效；独立线程身份过滤过期导航结果。更换编码器/内容类型走完整频道重置流程。
- 换台/释放播放器取消旧解析线程；轮询检查中断和已被替代的请求，使用单调时钟；等待间隔从 80ms 改为 250ms，状态读取限制连接/读取超时。
- CPU 采样最短间隔 2 秒，/proc/stat 可读但尚无增量时不再误触发 sysfs 全核扫描。
- 隐藏底部频道卡片时不更新其视频信息文字；媒体接口使用真实低资源标记，使 4.4 管理端采用较低刷新频率。

## 验证

- ARM32/ARM64 release 构建成功，23 项控制网页回归及网页媒体暂停/恢复测试通过。
- 央视网/B站四次正常切换，以及随后十次快速切换：已有串流 prepared 一直为 true，播放时钟连续增长。日志记录 retained decoder；仅初次播放有一次 First video frame / 解码器初始化。
- 快速切换的控制请求加一次状态读取耗时 68～217ms；这是控制接口响应时间，不是网页完整加载时间。
- 接收端截图确认 B 站页面显示正常。
- 跨内容类型回归：首次发现需走完整代理重置路径，补齐后最终包从网页切至 CCTV-1 约 4 秒 prepared，再切回 B 站约 3 秒 prepared；正常同串流网页切换仍保持解码器。
- 稳态 B 站页面的两次 10 秒进程 CPU 样本分别 97 和 106 ticks，未显示可靠下降，不报告总 CPU 降幅。此次可确认减少的是切换时解码器重建、过期轮询和重复采样开销。

复测材料位于 .codex-tmp/tv-retained-final.log、retained-switch-results.json、tv-final.png；临时材料不纳入版本库。测试结束退出两端应用。
