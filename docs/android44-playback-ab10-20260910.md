## 测量口径与限制

- 从设备端 NtvBench 标记至同频道 `First video frame rendered` 日志，两端点使用设备时钟；不以 HTTP 请求完成作为出画。45 秒为每次请求完成后的观察窗口。计时包含控制请求、旧播放清理、解析、下载、解密及首帧渲染。
- 保持 high 画质、stable 延迟模式、auto 解码、关闭自动换源。成功样本两版央视频实际均为 1920×1080，央视网实际均为 1280×720；首帧均为硬件解码。
- 这是已安装并配置好应用的单轮切台对比，不是清空数据后的冷启动基准；直播分片、网络状态随时间变化。没有在测试中改动应用代码或安装插件。
- 覆盖安装保留了地址缓存：本轮当前央视频需重新解析，线上 10 个央视频均命中缓存。差值不能全部归因于版本代码；当前解析接口日志通常较短，另有明显的解密耗时。
- 旧版不支持 `/api/media` 与 play 请求的 source 参数。央视频使用第 1 源；央视网通过 ADB 右方向键切至第 2 源，逐次核验 sourceIndex=1、CCTV 解密模式和 720p 实际输出。旧版央视网计时包含额外的遥控器操作和短暂启动第 1 源的开销，因此并非完全相同的控制路径。
- 已丢弃旧版忽略 source 参数而播放央视频的错误线路样本，保留于 `online-invalid-source-selection.json` 和 `invalid-online-cctv-*`，没有计入本报告。
- 截图用于抽查实际画面，取于首帧之后；统计依据首帧日志，不以截图文件落盘时间计时。

## 日志揭示的耗时

1. 当前包存在等待上一频道分片解密结束的开销。例如当前央视网 CCTV-1：13:58:14.143 发指令，13:58:18.443 才完成 CMG 会话重置，相差 4.30 秒；其间提示 worker still stopping。
2. 当前央视网 CCTV-1 首播门限等待两个分片，日志为 downloadMs=1370、decryptMs=9264，总门限等待 10.634 秒。这一个样本的主要等待是分片解密，不是 HTTP 接口解析。
3. 当前央视频 CCTV-10 新分片解密为 4545ms / 1,981,896 bytes；线上同频道新分片为 3404ms / 3,189,796 bytes。分片内容不同，不能当成严格同输入微基准，但提示应优先核查当前插件的解密实现和构建优化。
4. 当前/线上均有慢频道和网络超时。后续优化应针对旧解密任务取消、解密效率和首播门限，并以同一固定分片单独复测，不能仅根据本轮总时间认定脚本下载是瓶颈。
