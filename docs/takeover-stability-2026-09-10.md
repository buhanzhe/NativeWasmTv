# 接管稳定性与实验性直连开关

## 当前默认行为

“投屏与互联 → 接管电视”增加 Wi-Fi Direct（实验性）开关，默认关闭，使用路由器 IP。仅用户主动开启后才启动后台直连；开关保存在本机。接管中禁止修改，提示先结束接管，避免拆断当前媒体连接。

实验性直连暂不作为推荐路径。本轮最初的 Direct 复测中，首次可建立连接，但后续重连出现超时并留在 LAN，未达到稳定快速重连要求。后续验证转为默认路由器模式。

## 修复

- 接管/退出请求互斥，避免网页重复点击启动多个会话；重复接管当前电视直接返回已有连接。
- 退出时先取消本地直连任务、停止会话并恢复手机，再发短超时退出通知，避免离线电视拖住本机退出。
- 手机发给电视的退出通知携带会话 ID，电视在执行时校验；过期通知不会清掉后来建立的接管。
- 领取会话时携带预分配 ID；网络请求期间若用户已退出，完成回调不能重新启动接管，并按 ID 清理旧领取。
- 接管页面返回成功前完成本机 UI 状态提交，减少立即退出时旧回调重新进入接管。
- 普通 LAN 退出不再对空闲 P2P 状态调用 removeGroup，减少无意义的系统操作。

旧电视若不认识新的 endTakeover 指令，将依靠既有心跳租约退出；未恢复不带会话校验的强制清空方式。

## ADB 实机验证

手机：MI6 Android 7.1.1（ff0316c7）；电视：Android 4.4.4（8ba8ceb8）。同一路由器，手机 192.168.0.114，电视 192.168.0.113。保留包名 xiao.bu.tv，覆盖安装，不清除数据。

| 测试 | 结果 |
| --- | --- |
| 默认值 | experimental=false；没有 P2P 组，没有后台升级 |
| 完整接管、播放、退出 8 轮 | 8/8；接管 CCTV8K 均 prepared/playing=true，退出恢复电视原 CCTV-4 选择 |
| 领取后立即退出 5 轮 | 5/5；双方无接管残留，电视频道恢复 |
| 已接管时再次接管 | 返回已有连接，不重建会话 |
| 向电视注入过期会话退出通知 | 当前播放和连接保持 |
| 同时提交 6 个接管请求 | 1 个成功，5 个返回正在处理；无重复会话 |
| 接管中修改 Direct 开关 | 拒绝并提示先结束接管 |
| 空闲开启、重启、关闭 | 开启值跨重启保存；最终恢复关闭，Direct idle |
| force-stop 电视应用 | 手机约 3225 ms 退出接管，恢复最后 CCTV8K 选择 |
| force-stop 手机应用 | 电视约 3440 ms 退出接管，恢复原 CCTV-4 选择 |

完整接管到电视播放状态就绪约 3.59–5.19 秒，包含节目重新加载，不是网络连接延迟。正常退出到频道选择恢复约 0.35–1.14 秒。3 秒租约测试数值包含 ADB 命令和轮询观测时间。

限制：原 CCTV-4 在基线就未播放成功，因此验证的是恢复原频道选择，不宣称其重新出画面成功。异常断开采用强制结束应用，并非真实断电或 Wi-Fi 射频丢包；没有宣称全天稳定性。真实播放器出画面已由接管过程的 CCTV8K 验证，未完成网页/多媒体所有类型的长期测试。
