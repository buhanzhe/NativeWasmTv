# 投屏体验建议与高规格测试状态

基于当前私有合并工作区代码，2026-09-08。

## 建议的主流程

播放频道或网页 → 点击“投屏” → 选择电视 → 自动进入控制面板。

投屏期间固定显示设备名称、当前内容和“结束投屏”。返回键只返回上一级页面；结束投屏恢复电视原节目，手机继续显示正在投送的内容。

### 优先处理

1. **统一称呼与入口。** 用户界面统一使用“投屏到电视”“正在投屏”“结束投屏”。“接管”“飞鼠”“投送”作为内部实现或次级说明即可。网页悬浮按钮和管理页使用同一个设备选择面板、同一个连接状态。
2. **先选设备。** 主面板显示最近设备和当前在线设备；IP 输入放入“手动添加”。没有设备时留在同一面板，提供重新搜索与手动添加，避免跳到完整设置页。保留最近十台设备，但点击时再次检查是否可达。
3. **连接后立即可控。** 网页默认进入大触控板；频道默认进入简洁的频道控制。底部保留频道选择和结束投屏。键盘、陀螺仪、校准、游戏手柄归入“更多”。手机后台承载虚拟屏时，前台直接显示控制器，减少黑色说明页与管理页之间的跳转；默认不增加实时预览的额外渲染开销。
4. **连接过程可取消。** 显示“寻找电视／建立连接／电视准备画面”，提供取消和重试。取消后作废本次连接任务，避免迟到的网络或权限回调又把电视接上。进度百分比没有可测分母时，用阶段文字代替。
5. **优先尽快出画。** 建议将此前的“同路由器优先 Direct”调整为“最快可用链路优先”：复用已就绪的 Direct；首次连接先使用可达的局域网。Direct 放入连接优化选项，经过验证后记忆。热点和有线接收端沿用局域网。切换链路须保留失败回退，避免每次打开投屏都重新组网。
6. **配置与实际效果分开显示。** 主面板只放“流畅／清晰／自定义”；分辨率、帧率、编码和码率移入设置。显示实际生效的分辨率、帧率、编码，以及降级原因。调整一组参数后统一应用，并明确是立即重启投屏还是下次生效。

## 代码中确认的体验冲突

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| control/pages/cast.html | IP 输入、连接和多项编码参数都在一级页面 | 首次操作需要理解太多配置 |
| control/js/pages/cast.js | 未运行投屏时也显示“电视在线” | 容易把管理页可访问误解为已连接接收端 |
| MainActivity.startCastFromEdge | 找不到设备后打开完整投屏管理页 | 操作上下文发生跳转 |
| MainActivity.handleWebTakeover | 悬浮入口与管理入口通过 stayOnContent 分别处理导航 | 同一个投屏动作出现不同落点 |
| control/pages/flymouse.html | 触控板、全键盘、游戏手柄与陀螺仪同时占用显著位置 | 常用控制需要从多个模式中辨认 |
| receiver_takeover_overlay.xml | 黑色说明页要求再点击返回管理界面 | 投屏成功后没有立即提供主要控制 |
| control/js/pages/cast.js | 每次参数变动立即保存，提示“下次投屏生效” | 所选参数与当前画面可能不同 |
| RemoteCatalogClient.resolve | 低资源接收端发送 castFps=25，最高 1920×1080、码率上限 4 Mbps | 4.4 接收端不能通过普通界面真正试出 30/60fps |
| MainActivity.buildRemoteReceiverCastConfig | 再次执行接收端上限约束 | 设置 60fps 不等于实际以 60fps 编码 |

建议在内部收敛为单个投屏会话状态：未连接、寻找设备、连接中、投屏中、重连中、结束中、失败；网页、悬浮入口和原生控制器统一读取。分别保留“用户期望参数”和“当前协商参数”，以免页面互相覆盖状态。

## 两台实机与测试状态

- 发送端：小米 6，Android 7.1.1，192.168.0.114。
- 接收端：三星 SM-G3608，Android 4.4.4，192.168.0.113。
- 两台设备当前连接同一 Wi-Fi。
- 测试使用独立应用 ID，避免覆盖原有频道及配置。测试包已构建；4.4 接收端已成功安装、启动测试探针。
- 小米 6 安装测试包失败，系统返回 `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`。已请求用户允许 USB 安装。
- 小米 6 现有主应用安装包未提供当前投屏接口，不能用于替代当前版本进行本轮发送测试。

**本轮尚未得到两机投屏的高分辨率、高帧率实测结果。** 不能将旧日志、普通频道解码帧率或仅修改配置作为投屏测试结果。

## 授权安装后的测试矩阵

先验证正常连接所协商的实际参数，再通过独立测试探针逐项尝试更高参数，不修改正式版的低资源保护规则。

| 档位 | 目的 |
| --- | --- |
| 720p / 25fps | 当前兼容基线 |
| 720p / 30fps、60fps | 单独验证提高帧率的收益和排队风险 |
| 1080p / 25fps、30fps、60fps | 验证更清晰画面与帧率的平衡 |
| 1440p / 30fps | 根据 1080p 稳定性决定是否继续测试 |

每档记录实际编码尺寸与帧率、接收端解码/输出帧率、缓存增长、丢帧、码率和异常。使用持续变化的测试画面；同一图像内包含时间标记，截图对时需要同时给出时钟与截图采样误差，不能用编码耗时加网络 RTT 冒充端到端延迟。

按当前实现，7.1.1 的网页投屏测试为仅画面模式。频道原地址交由电视直接播放时，音频由电视解码，这与网页画面编码投屏是不同路径。

在没有实测结果前，保留现有稳定档位，不建议直接把 4.4 接收端默认值提升到 60fps。最终档位应同时满足画面流畅和缓存不持续增长。
