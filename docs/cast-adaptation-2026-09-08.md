# 投屏编码观测与自适应

## 行为

- 用户设置是本次投屏的初始目标，不改写已保存设置。短暂尖峰不触发分辨率变化。
- 每 500ms 观察一次负载；编码链路 P95 大于 max(60ms, 两个帧间隔)，或已提交帧持续未输出超过 max(150ms, 四个帧间隔)，判为编码链路压力。
- 连续两个异常窗口先将目标码率降低 25%，码率调整至少间隔 1.5 秒。发送拥塞也可以降低码率，但不能单独触发分辨率下降。
- 编码压力持续至少 12 个窗口，且码率已降至初始目标的 60% 以下或下限，才考虑降分辨率；拒绝动态码率的厂商编码器仍能进入该路径。
- 分辨率按 2160→1080→720→540→360 档降低，宽度等比例取偶数；帧率保持本次协商值。开始投屏 10 秒内不降分辨率，两次分辨率调整间隔至少 15 秒。压力恢复即取消待执行降档。
- 码率连续健康 20 秒后小步恢复；本次会话不自动升分辨率，避免往返切换。下次投屏重新采用用户配置。
- 视频切换保留 RTSP、控制连接与音频捕获，重新发送新编码器的 SPS/PPS 和关键帧。失败尝试恢复上一个编码配置，恢复失败则按已有投屏失败流程退出。
- 保留 WebView 的绘制 Surface、输入尺寸和 GL 上下文，GPU 将原画面缩小到较低的编码输出尺寸。这样减少编码像素量，网页布局和光标位置保持稳定；并不降低页面自身的 DOM/Canvas 绘制复杂度。

## 指标含义

`encodeDelayMs` 用输入 Surface 的 PTS 与同一帧的编码输出配对，统计最近两秒的均值。`encodeP95Ms` 是该窗口的第 95 百分位，不再用未配对的时间差近似。

| 字段 | 含义 |
|---|---|
| surfaceSubmitMs | eglSwapBuffers 提交调用耗时均值，含 Surface 背压 |
| afterSubmitMs | 提交返回后到取出编码结果的耗时均值 |
| encoderPendingFrames | 已提交而尚未完成配对的帧数 |
| encoderOldestPendingMs | 最老未完成帧的等待时间 |
| encodeSamples / encodeUnmatchedFrames | 有效样本数 / 找不到输入 PTS 的输出数 |
| videoQueueDelayMs / videoSendDelayMs | 编码后应用发送队列等待 / 发送调用耗时 |
| encoderTargetBitrateMbps / adaptationStatus | 当前目标码率 / 自适应原因 |

输出可能先于另一个线程的提交调用返回，因此提交耗时与提交后耗时不能始终相加等于总耗时。环形历史最多 256 帧，统计每秒两次，无逐帧日志或无界容器。

这些指标精确配对了应用能观察到的提交与输出事件，仍含 GPU 完成、编码器内部队列和输出线程调度，不能声称是芯片纯编码计算时间。MediaCodec 不提供所有厂商通用的纯硬件耗时接口。UDP 发送返回也不等于电视已收到全部数据；提高码率后延迟增大仍可能来自无线链路或接收缓存。

API 依据：https://developer.android.com/reference/android/media/MediaCodec

## 验证与当前限制

- JVM 回归通过：PTS 乱序与输出早于提交返回、样本过期、固定内存上限、短暂尖峰、持续编码压力、纯网络拥塞、无接收端、厂商拒绝码率调整、压力恢复取消降档、分辨率下限与配置不回写。
- 网页控制回归 12 项通过；ARM32 / ARM64 debug 和签名混淆 release 构建通过，包名仍为 xiao.bu.tv。用于强制触发降档的接收器仅存在于 debug，受系统 DUMP 权限保护。
- 小米 6（Android 7.1.1）到 Android 4.4.4 接收端，协商实际为 25fps。初版 720p/4Mbps 的一轮 PTS 配对样本：均值 19ms、P95 22ms、提交 1ms、待完成 0、未匹配 0。测试触发 540p / 360p 后短期可持续显示画面，均值约 15ms / 13ms。这些是测试页面及当时实现的数据，不是最终版本长期稳定性或红米 K30 Ultra 的性能结论。
- 延长测试遇到 MI 6 的 Adreno-GSL / Chrome_InProcGp 崩溃；随后未投屏、仅打开相同 Canvas 网页也能发生同类崩溃，不能仅归因于自适应降档。保留绘制输入缓冲尺寸的最终调整尚待完整复测。
- 重启手机排除驱动残留状态后，设备处于首次解锁前的加密锁定状态，需要用户手动解锁才能继续启动应用。未绕过锁屏。最新签名包属于待实机验证的测试构建。
- 未完成红米 K30 Ultra、系统音频开启、最终版本长时间连续降档与端到端延迟对照测试；不会将较低 encode 数值当成整体低延迟保证。

本地证据在 `.codex-tmp/cast-study/adaptive-timing-*.json`、`adaptive-tv-*.png` 和 `adaptive-preserved-baseline.json`，不纳入发行包。设备解锁后需完成最终降档复测，并移除 cast_adaptive_test 临时频道、恢复测试前手机设置；测试前快照为 `adaptive-phone-before.json`。


## 2026-09-09 复测更新

手机已解锁并复测。ARM64 和 ARM32 均可完成强制 720p→540p→360p 的编码输出切换，期间连接保持；但延长测试仍出现 WebView/原生渲染进程崩溃。ARM32 记录包含 RenderThread / libhwui.so 的 SIGSEGV，不能认定仅 64 位受影响，也不能宣称前述 Surface 保留调整已经修复崩溃。未继续扩大未经证实的驱动兼容改动。

较轻的 DOM/CSS 动画页面下完成 UDP 协议验证，30 秒内编码帧数从 163 增至 789，电视实际采用 UDP。TCP 在此前 Canvas 投屏中也由接收端日志确认。小米 6 此轮编码均值约 12–17ms，而 TCP 应用发送/等待指标曾到数百毫秒；这些指标含先前尖峰的平滑保留，不能相加作为即时端到端延迟。

设备临时频道和设置已清理恢复，投屏传输选择恢复默认 TCP。红米 K30 Ultra 和真实 H.265 接收画面仍未实测；本地 4.4 接收端不支持硬件 HEVC，正常协商回退 H.264。
